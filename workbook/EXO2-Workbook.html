THE SHAPE OF IT

One endpoint in, many providers out

Everything below the gold line is replaceable. Everything above it is the contract your clients depend on.

THE WHOLE ARCHITECTURE, COMPRESSED

The resolver never imports the plugin.

That single fact explains the folder structure, the naming rules, configuration.yaml, and why adding a second commerce backend is a config change rather than a rewrite.

Feature — the contract

An abstract class describing what a capability does. Provider-agnostic. Knows nothing about Shopify, Postgres or Klaviyo.

Plugin — the implementation

A concrete class implementing that contract against one specific provider. All vendor knowledge is quarantined here.

configuration.yaml — the wiring

Decides which plugin satisfies which feature, per consumer. The only place the two sides meet.

The test you will apply all course

If a file under features/ contains a vendor's name, a URL, or an SDK import — it is in the wrong folder. That is the single most common off-pattern mistake, and the one Bob makes most often when under-prompted.

READING THE TRACE

Three things that trace proves

1 · The seam is step 7

Everything above it is client-facing and stable. Everything below it is vendor-specific and disposable. Every architectural argument you will have is about which side of that line something belongs on.

2 · Errors are a feature concern

The plugin catches the vendor's error and throws BlogErrors.getBlogsFailed() — declared in features/blog/blog.error.ts. Clients never see a Shopify error code.

3 · The mapper is not optional plumbing

It is the thing that makes the swap possible. A "quick" fix that returns a vendor field straight through has just welded the client to Shopify.

NAVIGATION · WHERE CODE LIVES

Three layers, one rule

Every file sits in exactly one. Which one tells you what you may do to it.

core/

The framework engine — foundation/ api, server, feature, plugin, datastore, context, error.

Never edit.

core-modules/

Standard capabilities the platform ships — commerce, account, navigation, user… plus the Shopify and Postgres providers.

Consume, do not edit.

src/apps/exo-cerebrum/

Your application — the features and plugins the platform does not ship, plus configuration.yaml.

Yours. The only layer that changes.

Two ways the app reaches down

// SHADOW — an Ext* class in src/apps/ wins over core/
class ExtAuthorizationGuard extends AuthorizationGuard

// EXTEND — inherit a standard model, add your fields
import { Product } from '@feature-commerce/product';
export class ExtProduct extends Product { }

The import tells you the layer

  • @api @feature @guards → core/
  • @feature-commerce @plugin-shopify → core-modules/
  • @apps/exo-cerebrum/… → your app

If a fix means editing the lower two, you have missed an extension point — and framework upgrades will cost you every patch by hand.

THE SWITCHBOARD

configuration.yaml — the one file that wires the app

Top to bottom, in file order. Nothing here is registered in code — click any block for the real YAML and what it controls.

1 appName · graphqlPath · swaggerPath identity and the served surfaces IDENTITY 
appName: exo-cerebrum
swaggerPath: swagger
graphqlPath: graphql

appName is why the start command is yarn start exo-cerebrum — one repo can hold many apps under src/apps/, each with its own configuration.yaml. The two paths are literally the URLs served: :3100/graphql and :3100/swagger. Change graphqlPath and the playground moves.

2 defaultServiceGuard · doAPIUserAuthorizationByDefault global auth switches SECURITY 
defaultServiceGuard: false
doAPIUserAuthorizationByDefault: false
doAPIAccessControl: false

Auth is decided in two places, and this is the first: the global default. The second is per operation — isAuthRequired in each <feature>.api.configuration.ts. Both flags are false here, so the global guard runs on every request but enforces nothing, which is why the app needs no identity provider. Flip these two to true in the final session and every operation 401s until the guard is implemented.

3 logger · loggerMaskedFields · locales observability and language RUNTIME 
appBootDebug:
    logEntities: true
logger: winston
loggerMaskedFields:          # redacted everywhere they appear in logs
    - password
    - clientSecret
    - access_token
locales:
    - id: &locale-en-us en-US
      default: true
spelunkerEnabled: true       # exposes the DI graph for inspection

loggerMaskedFields is the one to point at — secrets are redacted by name wherever they appear in a log line, which is why you can safely turn on verbose logging in a shared environment. Note locales uses an anchor too (&locale-en-us); anchors are not special to plugins.

4 consumers who is calling — bindings are per consumer CALLERS 
consumers:
    - id: &training-app training-app
      enabled: true
      default: true

A consumer is a caller: the web console, the mobile app, an internal service. This is the concept most people miss — a feature is bound to a plugin per consumer, so the same getBlogs can resolve to Shopify for one caller and a CMS for another, from one running server. It is also the second way to make an operation vanish: leave the feature enabled but omit your consumer id, and it looks exactly like a missing resolver.

5 databases commented out — Stage 2 only DATA 
# databases:
#     - id: &ase-database ase-database
#       type: postgres
#       enabled: true

# NOTE: there is no `messengers:` block either — Kafka is out of scope.

Absent on purpose, so the app needs no Postgres to boot. Uncomment this without a running Postgres and the app does not degrade — TypeORM retries ten times at three-second intervals and then fails to start, taking products and blogs down with it. Worth knowing: the loader does guard against a missing messengers or consumers block. It does not guard adminFeatures — see the last row.

6 plugins declares each provider ONCE, and names it PROVIDERS 
plugins:
    - id: &shopify shopify        # & DEFINES the anchor
      name: Shopify
      type: commerce
      configuration:
          tokenPurseId: shopify
      variants:
          - id: 2025-10                 # API version pinning
            configuration: { apiVersion: 2025-10 }
      consumers:
          - id: *training-app
            pluginDefaultConsumer: true
            configuration:
                menus:                  # read AT BOOT by the category registry
                    rootCategory: { id: main-menu:Catalog, depth: 4 }

&shopify is a native YAML anchor — it declares a name that the rest of the file can point at. Everything about the provider lives here once: credentials pointer, API version variants, and per-consumer configuration. Extend it by adding a provider block; you do not touch any feature to do so.

7 features turns capabilities on and points them at a provider THE SEAM 
features:
    - id: health
      enabled: true
      standalone: true          # no plugin at all — answers for itself

    - id: commerce                # a GROUP; children inherit nothing automatically
      features:
          - id: product
            enabled: true
            plugins:
                - id: *shopify    # * REFERENCES the anchor — THIS IS THE SEAM
                  consumers:
                      - id: *training-app

    - id: blog
      enabled: true             # false ⇒ the field leaves the SCHEMA entirely
      plugins:
          - id: *shopify
            consumers: [ { id: *training-app } ]

Three things live here. enabled — set it false and the field is not an error, it does not exist in the schema. *shopify — the reference that binds contract to implementation; change it and the whole implementation swaps with nothing above it moving. standalone: true — no plugin at all, the feature answers from its own resolver. Note plugin: singular is used for datastore-backed features and plugins: plural for the rest.

8 adminFeatures empty — but the key must exist GOTCHA 
adminFeatures: []

Delete this key and the app dies at boot with TypeError: Cannot read properties of undefined (reading 'forEach'). The ConfigurationLoader iterates adminFeatures without checking it is defined — unlike messengers and consumers, which are guarded. An empty array satisfies it. This is a real trap, not a hypothetical: it is exactly what broke this config the first time it was written.

Editing this file does not hot-reload. The app reads its config from dist/, and nest start --watch only restarts on TypeScript changes. After editing, save any .ts file — or restart — before the change takes effect.

NAVIGATION · GOLDEN PATH EXEMPLAR

Anatomy of a feature — features/blog/

In the order they participate in a request. Every feature in the codebase is this same set — click any row for the real code and how you extend it.

1 blog.module.ts registers the feature and exposes its token BOOT 
import { BaseFeatureModule } from "@feature/module";

export class BlogModule extends BaseFeatureModule { }

Two lines, and you will almost never change them. It exists so BlogModule.feature is a token the resolver and every decorator can reference. Extend it only when a feature needs its own DI providers.

2 blog.api.configuration.ts declares the operations — id, auth, REST shape DECORATOR 
static operations: BlogApiOperations = {
    getBlogs: {
        id: 'getBlogs',
        description: 'Get blogs',
        isAuthRequired: false,      // per-operation auth
        queryOptions: { required: false },
    },
};

static getBlogs(): ApiOperationOptions {
    return this.composeOperationOptions(this.operations.getBlogs);
}

Read at class-definition time by the resolver's decorator, not per request. Extend it by adding an operation, or by flipping isAuthRequired — that single flag is what the final session's guard lab toggles.

3 blog.parameters.ts defines the arguments the operation accepts DECORATOR 
export const BlogRequestParameters: BlogRequestParametersType = {
    ...RequestParameters,          // inherits pagination, locale…
    blogHandle: {
        id: 'blogHandle',
        description: 'Blog container handle (e.g. "news")',
    },
};

The spread is the part to notice — ...RequestParameters gives you pagination for free, which is why the resolver can accept it without declaring it. Extend it by adding a key, then referencing it from an @Args.

4 blog.resolver.ts the request enters here — and delegates REQUEST 
@Resolver(() => Blog, { feature })
export class BlogResolver extends BaseFeatureResolver {

    @Query(() => BlogResultSet, BlogApiConfiguration.getBlogs().queryOptions, feature)
    async getBlogs(
        @Args({ parameter: BlogRequestParameters.blogHandle, required: true })
        blogHandle: string,
        @Context() context: any,
    ): Promise<BlogResultSet> {
        // THE DELEGATION MOMENT — asks for the ABSTRACT class
        const { requestContext, service } =
            this.getRequestContextAndService<BlogService>(context, BlogService);

        return await service.getBlogs(blogHandle, requestContext, pagination);
    }
}

No new. No import from plugins/. It names only the abstract class and is handed whatever configuration.yaml bound for this consumer. Extend it by adding a @Query or @Mutation — but add the abstract method in step 5 first.

5 blog.service.ts the contract — signatures, zero implementation REQUEST 
export abstract class BlogService extends BaseFeatureService {

    /** Fetch a single blog article */
    abstract getBlog(
        blogHandle: string,
        articleHandle: string,
        requestContext: RequestContext,
    ): Promise<Blog>;

    abstract getBlogs(
        blogHandle: string,
        requestContext: RequestContext,
        pagination?: PaginationInput,
    ): Promise<BlogResultSet>;
}

The most important file in the folder, and it contains no logic at all. This is always the first file you edit. Add an abstract method here and every plugin implementing BlogService stops compiling until it provides one — the compiler enforces the contract for you.

6 blog.model.ts the shape the client receives RESPONSE 
@ObjectType({ description: 'EXO Blog Article' })
export class Blog {

    @Field({ description: 'SEO Friendly handle' })
    handle?: string;

    @Field({ type: () => [String], description: 'Article tags' })
    tags?: string[];
}

@ObjectType()
export class BlogResultSet extends ResultSet<Blog> {
    @Field({ type: () => [Blog] })
    results?: Blog[];        // note: results, not items
}

Pure vocabulary — your words, never the provider's. Extend it by adding a @Field, then mapping it in the plugin's mapper. Nothing else changes; the resolver never moves.

7 blog.error.ts failures the client is allowed to see FAILURE 
protected static errors: BlogErrorsType = {
    ...FeatureErrors.errors,
    getBlogsFailed: {
        code: 'EXO_BLOG_LIST_FAILED',
        message: 'Failed to retrieve blog list',
        statusCode: 400,
    },
};

static getBlogsFailed(): HttpException {
    return this.composeHTTPError(this.errors.getBlogsFailed);
}

Owned by the feature, thrown by the plugin. That is deliberate: the plugin catches whatever Shopify threw and rethrows one of these, so a vendor error code never reaches a client. Extend it with a new entry plus its static factory.

8 index.ts the surface the plugin imports from EXPORTS 
export * from './blog.module';
export * from './blog.model';
export * from './blog.service';
export * from './blog.error';

// the plugin then does:
// import { Blog, BlogErrors, BlogService } from '@apps/exo-cerebrum/features/blog';

The barrel is how the plugin reaches the contract without importing individual files. Do not add a package.json beside it — an empty one breaks directory resolution at runtime while still compiling clean.

NAVIGATION · THE OTHER SIDE OF THE SEAM

Anatomy of a plugin — plugins/commerce/shopify/features/blog/

Four files, same request order. Everything Shopify knows about lives here and nowhere else.

1 shopify.blog.module.ts registers the plugin's components BOOT 
import { ShopifyBaseModule } from "@plugin-shopify/common";

export class ShopifyBlogModule extends ShopifyBaseModule { }

// at boot the loader resolves classes BY FILENAME:
//   **/shopify/features/blog/**/*shopify.blog*.service.js

One line again — the work is done by the base class. Note what it logs at boot: components are discovered by file-name glob, not by import. That is why <provider>.<feature>.<role>.ts is not a style preference — misname a file and it is simply never found.

2 shopify.blog.service.ts implements the contract, orchestrates the other two REQUEST 
export class ShopifyBlogServiceImpl extends ShopifyBaseServiceImpl
    implements BlogService {          // the contract from the feature side

    async getBlog(blogHandle, articleHandle, requestContext): Promise<Blog> {
        const ds     = this.getBlogDatasource(requestContext);
        const mapper = this.getBlogMapper(requestContext);

        try {
            result = await ds.getArticleByHandle(requestContext, blogHandle, articleHandle);
        } catch (error) {
            throw BlogErrors.getBlogFailed();   // FEATURE error, not Shopify's
        }

        if (!article) throw BlogErrors.getBlogNotFound();

        return mapper.mapArticle(requestContext, article);
    }

    protected getBlogDatasource(rc) { return this.getDatasource<ShopifyBlogDatasource>(rc, ShopifyBlogDatasource); }
    protected getBlogMapper(rc)     { return this.getMapper<ShopifyBlogMapper>(rc, ShopifyBlogMapper); }

It fetches nothing and maps nothing — it coordinates, and it translates failure. Extend it when you add an abstract method to the feature service: TypeScript will refuse to compile until you do, which is the contract enforcing itself.

3 shopify.blog.datasource.ts the only file that performs I/O I/O 
export class ShopifyBlogDatasource extends ShopifyBaseDatasource {

    private readonly ARTICLE_FIELDS = `
        id  title  handle  contentHtml  excerpt  publishedAt  tags
        authorV2 { name email }
        image { url altText width height }
        blog { handle title }
    `;

    async getBlogArticles(requestContext, blogHandle, first, after) {
        return this.executeGQL(requestContext, {
            id: 'getBlogArticles',
            method: 'post',
            query: { queryId: 'getBlogArticles', query: `…${this.ARTICLE_FIELDS}…` },
        }, { blogHandle, first, after });
    }
}

Returns Shopify's raw payload, untouched. It must not map — one transformation in here and the mapper stops being the boundary. Extend it only when the vendor genuinely is not sending the data yet; check ARTICLE_FIELDS first, because it often already is.

4 shopify.blog.mapper.ts vendor vocabulary becomes yours RESPONSE 
export class ShopifyBlogMapper extends ShopifyBaseMapper {

    mapArticle(requestContext, dsArticle): Blog {
        if (!dsArticle) return null;

        const model = new Blog();

        model.handle    = dsArticle.handle;
        model.content   = dsArticle.contentHtml || dsArticle.content || null;
        model.author    = dsArticle.authorV2?.name || null;   // flattened
        model.image     = dsArticle.image?.url || null;      // altText/width/height dropped
        model.tags      = dsArticle.tags || [];

        return model;
    }
}

The boundary. After this line no Shopify field name exists anywhere in the response — authorV2 became author, and that renaming is the whole reason the provider is swappable. It must not fetch. Look closely at the image line: the datasource asked for four fields and only one survives. That is your first lab.

Some plugin features add *.schema.ts (the vendor query document) and *.configuration.type.ts (typed per-feature config read from configuration.yaml). Nothing here may import another plugin.

Postgres sits behind exactly the same seam as Shopify. Only the middle of the pipeline changes — and the mapper survives, which is the whole point.

1 databases: declares the datastore and names it CONFIG 
databases:

Same anchor mechanism as &shopify — a datastore plugin will point at *training-database exactly as a commerce feature points at *shopify. Note what is not here: no host, no user, no password. Connection values are environment, never config.

2 .env where the connection actually comes from ENV 
PGHOST=localhost
PGPORT=5432
PGDATABASE=exo_training
PGUSER=postgres
PGPASSWORD=…
APP_DB_SCHEMA=training   # tables land here, NOT in public

The boot log prints every one of these back at you — except the password, which loggerMaskedFields redacts. APP_DB_SCHEMA is the one to remember: a bare \dt in psql reports "Did not find any tables" because it searches public. The tables are in training.

3 migrations/001_create_feedback.sql the schema, in version control SCHEMA 
CREATE TABLE IF NOT EXISTS __APP_SCHEMA__.feedback (
    id              uuid         PRIMARY KEY DEFAULT gen_random_uuid(),
    session_number  integer      NOT NULL,
    rating          integer      NOT NULL CHECK (rating BETWEEN 1 AND 5),
    comment         text,
    created_at      timestamptz  NOT NULL DEFAULT now()
);

It says __APP_SCHEMA__, not training. The runner substitutes APP_DB_SCHEMA at execution time, so one file runs unchanged against a different schema in every environment. Never hard-code a schema name in a migration. And never edit one that has already run — it is recorded as applied, so it is skipped and your edit silently does nothing. Add a new numbered file.

4 yarn migrate:feedback applies what has not been applied RUNNER 
# first run, on a machine with no database at all
Created database exo_training
Applying 001_create_feedback.sql
Applying 002_seed_feedback.sql
Migrations complete.

# run it again
Skipping 001_create_feedback.sql (already applied)
Skipping 002_seed_feedback.sql (already applied)

Idempotent by design — every applied file is recorded in a schema_migrations table, so this is safe to run on every deploy. Each migration runs in its own transaction, so a failure in 002 leaves 001 applied and recorded rather than half-done. A Postgres advisory lock stops two runners racing. Creating the database cannot be a migration: the runner must connect to it first, and Postgres refuses CREATE DATABASE inside a transaction.

5 the datastore plugin same four roles, different mechanics PLUGIN 
// the shape, alongside its Shopify counterpart

shopify.blog.datasource.ts     → executeGQL(...)          // HTTP
app-feedback-db.feedback.datasource.ts → repository.find() // SQL

shopify.blog.mapper.ts         → dsArticle.authorV2?.name
app-feedback-db.feedback.mapper.ts     → row.submitted_by

The service still implements the feature's abstract class. The datasource is still the only file doing I/O — it just holds a repository instead of a URL. And the mapper still turns the provider's shape into yours.

Ask the room: if a mapper only exists to protect you from a third party, why does this one need one? Because the client should not be coupled to your table shape either. Column renames, joins and denormalisation are your business, not the client's.

NAVIGATION · THE PROVIDER YOU OWN

Anatomy of a datastore plugin — plugins/app-feedback-db/

Six files. Same four roles as the Shopify plugin, with one difference worth stopping on: there is no datasource file — the TypeORM repository is the datasource, and the framework hands it to you.

1 features/feedback/app-feedback-db.feedback.module.ts registers, and finds the entities BOOT 
import { BaseDatabasePluginModule } from '@plugin-datasource-database';

export class FeedbackDbFeedbackModule extends BaseDatabasePluginModule { }

// what it logs at boot:
// Resolved database entities:
//   app-feedback-db\features\feedback\**\*app-feedback-db.feedback*.entity.js

One line, like every other module. But notice the log: entities are discovered by filename glob — nothing imports the entity here. The base class then calls TypeOrmModule.forFeature(entities, database.id) for you. Misname an entity file and it is silently never registered.

2 entities/app-feedback-db.feedback.entity.ts the TABLE, not the API SCHEMA 
@Entity({ name: 'feedback' })
export class FeedbackEntity {

    @PrimaryGeneratedColumn('uuid')
    id?: string;

    @Column({ name: 'session_number', type: 'int' })
    sessionNumber?: number;

    @Column({ name: 'submitted_by', type: 'varchar', length: 120, nullable: true })
    submittedBy?: string;
}

This describes the table — snake_case columns, varchar lengths, nullability. feedback.model.ts describes the API. They look alike today and diverge the moment you rename a column, add a join, or decide the client should not see a field. Nothing outside this plugin should ever see a FeedbackEntity.

3 common/db-app-feedback-db.base.service.ts where getRepository comes from BASE 
import { BaseDatabasePluginServiceImpl } from '@plugin-datasource-database';

export class DBFeedbackDBBaseServiceImpl extends BaseDatabasePluginServiceImpl { }

// what it inherits, from core:
protected getRepository<T>(entityClass): T {
    return this.moduleRef.get(
        getRepositoryToken(entityClass, this.plugin.configuration.database.id),
        { strict: false });
}

The plugin-local base class exists purely to inherit this. Look at the second argument: database.id — the string training-database from configuration.yaml. That is how an entity gets bound to one specific connection. Declare a second database and the same entity could be read from either.

4 features/feedback/app-feedback-db.feedback.service.ts implements the contract, runs the query REQUEST 
export class FeedbackDBFeedbackServiceImpl extends DBFeedbackDBBaseServiceImpl
    implements FeedbackService {          // the feature's abstract class

    async getFeedback(requestContext, pagination?) {
        const repository = this.getFeedbackRepository();   // ← the "datasource"
        const mapper     = this.getFeedbackMapper(requestContext);

        try {
            [entities, count] = await repository.findAndCount({
                order: { createdAt: 'DESC' }, take: limit, skip: offset });
        } catch (error) {
            throw FeedbackErrors.getFeedbackFailed();   // FEATURE error, not a PG one
        }

        return { results: mapper.mapFeedbackList(requestContext, entities),
                 pagination: mapper.composePagination(limit, offset, count) };
    }

    protected getFeedbackRepository(): Repository<FeedbackEntity> {
        return this.getRepository<Repository<FeedbackEntity>>(FeedbackEntity);
    }

Compare it to shopify.blog.service.ts — it implements the abstract class, catches provider errors and rethrows feature ones, and hands raw data to a mapper. Identical responsibilities. The repository simply replaces the datasource file.

5 features/feedback/app-feedback-db.feedback.mapper.ts row → feature model RESPONSE 
mapFeedback(requestContext, entity: FeedbackEntity): Feedback {
    if (!entity) return null;

    const model = new Feedback();

    model.submittedBy = entity.submittedBy ?? null;
    model.createdAt   = entity.createdAt
        ? new Date(entity.createdAt).toISOString() : null;   // Date → string

    return model;
}

The boundary, and the file people argue about. createdAt is a Date in the entity and a string in the API — types differ, not just names. Rename submitted_by in the database tomorrow and only this file and the entity change; the API is untouched. That is what the mapper buys you against your own schema.

6 common/db-app-feedback-db.base.mapper.ts pagination, computed not copied BASE 
composePagination(limit: number, offset: number, count: number): Pagination {
    const totalPages = count < limit ? 1 : Math.ceil(count / limit);
    const pageNumber = Math.ceil(offset / limit) + 1;

    return { page: pageNumber, pageSize: limit, resultCount: count,
             pageCount: totalPages, hasMorePages: pageNumber < totalPages };
}

Shopify hands back a cursor and hasNextPage, so its mapper just copies them. Postgres offers nothing of the kind — pagination has to be computed from limit, offset and a COUNT. Different provider, different pagination model, same Pagination object at the end. That is the seam doing its job.

Also here, outside the plugin's runtime code: migrations/*.sql and scripts/run-migrations.js. Those are a deploy-time concern — the runner never reads configuration.yaml and never loads Nest.

PHASE 4 · SESSION 1 — WORKED EXAMPLE OF THE FORMAT

Feature anatomy

Objective

By the end, each participant can open an unfamiliar feature folder and say what every file does without opening it — and can name which file a given change belongs in.

Lab

Add a getBlogTags operation to the blog feature. Contract first, implementation second.

Acceptance criteria — all four must hold:

  • Nothing under features/ mentions Shopify
  • The abstract service was edited before the plugin service
  • Failure throws a blog.error.ts error, not a vendor error
  • The app boots — an off-pattern component is rejected at load

Checking Bob's output

  • Grep the diff for the provider name under features/ — first and fastest check
  • Did it import from plugins/ into a feature? Reject.
  • Did it add a mapper, or return vendor fields raw?
  • Did it invent a filename? Compare against blog/ literally.

Exit ticket: name the file you would open first if getBlogTags returned null in SIT but worked locally.

THE DAILY HABIT · TEN MINUTES, EVERY SESSION

Trace It

Put a real response field on screen. Ask the room to name every file it passed through, in order. Week one they use the trace panel. Week three they will not need it — and that is the whole course, measured.

Ramp

  • Day 1–3 — trace panel visible, name the folders only
  • Day 4–8 — panel hidden, name the files
  • Day 9–12 — name the files, then say which would change for a given new requirement
  • Day 13–15 — given a symptom, name the file you open first and why

Starter prompts

  • A blog article's publishedAt is off by a timezone. Which file?
  • The client wants blogs paginated by 25. Which files, and which must not change?
  • Shopify starts returning 429. Where is that caught, and what does the client see?
  • A second commerce provider arrives. List everything that changes.
  • A feature works in Dev and 404s in SIT. What do you check before reading any code?

Answers to the last two: nothing above step 7 changes for a new provider — a plugin folder and one anchor in configuration.yaml. And the SIT 404 is enabled: or a missing consumer id, nine times in ten.
